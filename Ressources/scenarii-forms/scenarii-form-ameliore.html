Formulaire de demande de test

Titre clair et descriptif du test.
Exemples : – « Suppression d’un utilisateur par un administrateur » – « Vérification du message d’erreur lors d’un login invalide » – « Le bouton Export CSV génère bien un fichier valide »
Liste des éléments nécessaires pour exécuter le test dans de bonnes conditions.
Inclure : accès, rôles, comptes techniques, environnement, données à créer, pièces jointes, pré‑configuration.
Important : les tests ne doivent pas dépendre de données existantes en production ou en base. Toute donnée nécessaire doit être créée dans les étapes du test ou fournie ici en tant que ressource.
Exemples : – « Compte de test avec rôle ADMIN (à créer dans les étapes si nécessaire) » – « Accès à l’environnement de préproduction » – « Fichier PDF de test fourni en pièce jointe » – « Activation du module X dans la configuration de l’environnement »
Décrire précisément le protocole du test, étape par étape.
Inclure : navigation, actions, clics, saisies, URLs, interactions externes (app desktop, API…).
Exemples : – « 1. Se connecter avec le compte admin » – « 2. Aller sur /admin/users » – « 3. Cliquer sur le bouton Supprimer de l’utilisateur X » – « 4. Confirmer la suppression dans la popup »
Ce qui doit se produire pour considérer le test comme réussi.
Exemples : – « L’utilisateur n’apparaît plus dans la liste » – « L’API renvoie un status 200 » – « Un message “Suppression effectuée” apparaît » – « Le fichier exporté contient 12 lignes »
Détails précis pouvant invalider le test même si l’action principale semble fonctionner.
Exemples : – « Timeout > 5 secondes » – « Message d’erreur incorrect » – « Suppression effectuée mais liste non rafraîchie » – « API renvoie 200 mais payload incorrect »
